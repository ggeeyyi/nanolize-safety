agent 能作弊吗？nanolize 安全审查

nanolize 让一个全新的 coding agent 按功能契约重写仓库，再用原仓库的测试来检查结果。这份审查关心的是：如果这个 agent，或者它写出的代码，不去完成工作而是直接去拿“通过”的结论，会发生什么。下面列出目前守得住的部分、19 项问题，以及一条修复路线，路线参考了评测框架和 agent 沙箱对同类问题的做法。代码又前进 105 个提交之后做了第二轮复查：最初的 11 项没有一项关闭；新增的带沙箱 runner 能把文件藏起来，但 HOME 可写、网络开放。

01

摘要

只读这一节的话，记住四句话。

  1. 作者能改什么，防得很细。测试、测试运行器的配置、冻结的契约、作者工作区的 Git 状态，在每次调用作者前后都会检查，这些检查是有效的。
  2. 作者能读什么、它的代码在检查运行时能碰到什么，靠的是提示词。在默认 runner 上，作者的沙箱只限制写，所以原始源码、测试、冻结的期望输出和 held-out 任务都在 .. 一层之外。之后，检查又把作者的代码 import 进了负责报告结果的同一个进程。
  3. 新的 Claude Code runner 把文件藏起来了，却开了别的门。它的 bubblewrap 沙箱在黑名单写对的前提下，能让答案不可见。但同一个沙箱让 HOME 可写、网络开放，所以会话可以给 owner 的账号留下之后会被执行的程序，可以把凭证发出去，也够得着本地的 review 服务。
  4. 三处改动就能消掉大部分暴露面。一是由 nanolize 自己构建的白名单式读边界，覆盖每一种 runner；二是把候选检查放进沙箱并加上绊线；三是不信任工作区里出现的 agent 配置。带密钥的封印和轨迹审计负责收尾。

这其中不少话，nanolize 自己的文档已经说得很直白：作者边界“不是操作系统强制的读沙箱”，--allow-execution“不是沙箱”，新的适配器还附带一节“What the sandbox does not do”。这一页要做的，是把这些话的后果推演清楚，并说明怎样才能不再需要它们。

新代码做对的地方

  • 适配器不带 python -P 就拒绝启动；runner 命令漏了它，在配置时就会被拒绝。会话留在工作区里的任何东西，都不会在沙箱外被 import。
  • 适配器要运行的程序，在会话的 PATH 生效之前就解析好了。它不跟随工作区里的任何链接；会话的事件通过 socket 送达，会话自己的命令无法按路径打开它。

  • review 的控制通道不再经过环境变量里指定的代理；否则代理会拿到 control token。
  • 两端都有锚点的 schema pattern 改为匹配整个值。过去，末尾多一个换行也能通过。

03

对手是谁

不是外部攻击者。需要防的是 nanolize 自己启动的 agent，以及这个 agent 写出的代码。

作者并没有恶意。它在时间、token 和尝试次数的限制下追求“检查通过”，而现在的模型在捷径够得着的时候会去走捷径：

  • METR 报告过前沿模型在它的任务集上篡改打分代码、针对测试写特例，而且模型的表现说明它知道这不是用户想要的。[4]
  • ImpossibleBench 构造了测试与需求互相矛盾的编程任务，只要通过就一定是作弊。前沿模型会通过改测试、重载运算符或记录状态来通过其中相当一部分，而且模型越强作弊越多。把测试隐藏或设成只读能降低作弊率，更严格的提示词也有帮助。[3]
  • 伯克利一个团队的 exploit agent 没有解任何一道题，就在 SWE-bench Verified 上拿到 100%：一个 conftest.py hook 把所有测试结果改写成 passed。另外七个 agent benchmark 也被类似手法攻破。[2]

一个 nanolize job 里有三样东西值得保护：答案（原始源码、测试、冻结输出、held-out 任务）、结论（检查结果及其背后的封印记录）、owner 的机器（凭证、其他仓库、本地控制页面）。下表是今天各个角色实际够得着的范围。

04

问题出在哪一步

一个 job，六个步骤。问题集中在其中两步。

  1. 冻结采集并封存原始测试、期望输出和 held-out 任务。F3
  2. 作者重写全新的 agent 按契约写代码。“不看源码”靠指令，或者靠一份黑名单。F1F4F7F12F13F14F15F18
  3. 合入草稿并入候选版本。测试和运行器配置仍归 verifier，其他配置文件照单全收。F19
  4. 运行检查以 owner 身份，用原始测试跑候选版本。F2F5F6
  5. 修复反馈只说哪些义务没满足，不带测试内容和期望输出。守得住
  6. 交付状态来自验收报告，不由 agent 说了算。守得住

F8 到 F11、F16 和 F17 不在 job 内部，而在它周边：公开的 review 链接、agent 设计的测试、辅助 agent 读到的仓库文本和 agent 配置、依赖安装，以及谁能按下 Submit。

05

已经守住的部分

这些防线在代码里都能找到，审查中也没有发现绕过办法。后面的建议都建立在它们之上。

  • 命令。只执行 owner 授权过的 argv。controller agent 只能在阶段工具里选择，不能增加命令；job 的 argv 只有经过 owner 授权才会增加。
  • 环境变量。作者和 worker 进程拿到的是白名单环境，API key 和 bearer token 不会被继承。
  • 作者用不到 owner 的工具。默认作者运行时禁用了 plugins 和 apps，所以 nanolize 自己那些能读原始代码的 MCP 工具，它够不着。
  • 测试及其配置归 verifier。测试文件、conftest.py、pytest 和 tox 的配置节、launcher 配置（make、tox、nox、npm 等），候选版本都不能新增或修改。
  • 能发现 import 遮蔽。候选版本如果在检查的 import 路径上加入 sitecustomize、与标准库或测试工具同名的模块，或 .pth 文件，会被拒绝。
  • 作者工作区会被检查。不允许链接其他对象库，不允许有提交、引用或 remote；冻结的契约、知识包和反馈在每次调用作者前后都做哈希比对。
  • 修复反馈经过过滤。只带状态和作者自己代码里出错的那一帧，不带测试程序、期望输出和原始 traceback。
  • 任务评估有 held-out 的一半。hidden checks 在 solver 结束之后才进入工作区；judge 被告知 solver 的文本是不可信证据；轻量评分可以完全不调用模型。
  • 交付跟着证据走。controller 不能把失败的候选版本提升为成功。没跑的检查不算通过，超时算失败，delivered_with_failures 会阻止发布。
  • 背诵会被度量。original_overlap 按函数把作者写的内容和原始代码做比对，重复过多的草稿会被退回。

F1

作者读得到答案

高已复现

位置：execution.py:55 job_tools/freeze.py:311–312 rewrite.py:61

b96cf37 复查： 在 Claude runner 上部分缓解，黑名单可以把这些路径藏起来（探测 7）。默认的 Codex runner 没有变化。

默认作者是 codex exec --sandbox workspace-write，在 jobs/<id>/authoring 里启动。这个沙箱限制 agent 往哪里写，不限制它读什么。工作区旁边就是 worktree/ 和 original/，它们是 base commit 的两个 Git worktree，包含完整的原始源码和测试；还有带着全部期望输出的冻结 baseline，以及放着 held-out 任务和 hidden checks 的 task-effort/。再往外是原始仓库，以及读过原始代码的对话 agent 留下的会话记录。

现有防线为什么挡不住
  • 边界写在提示词里：“Do not use neighboring directories”、“Never search for hidden graders”。
  • _runner_argv_exposes 检查的是 runner 的参数，不是 agent 之后打开的文件。
  • original_overlap 度量的是与原始源码逐行重复的程度。照着测试断言或冻结输出写出来的代码一行都不重复；而且同一个文件被退回一次之后，下一次不管度量结果如何都会被接收。
后果
held-out 任务不再保密，--source-reference never 无法落实，“只依据契约写成”这句话在报告里站不住。

F2

候选代码自己报告自己的测试结果

高在玩具项目上复现

位置：verification.py:1468 verification.py:1323–1368 verification.py:55–66 leaf_test_validity.py:146

b96cf37 复查： 没有变化。verification.py 未被改动。

检查通过普通的 subprocess.Popen 以 owner 身份运行，网络开着，HOME 保留。每个用例的结论读自 pytest 写出的 JUnit 文件，而写这个文件的进程刚刚 import 了候选代码。候选包自己的代码可以在 import 时给 pytest 的报告对象或 unittest.TestCase 打补丁，也可以在退出时重写 sys.argv 里 --junitxml= 指向的文件。install-check 以同样的方式运行作者写的 build backend。

在一个玩具包上，函数故意写错，再加一段 import 时的补丁：pytest 打印 “2 passed” 并以 0 退出，nanolize 的 parse_junit 把两个用例都读成通过。去掉补丁的对照运行报告两个失败。这个实验没有走完整的 job 流程。

现有防线为什么挡不住
  • 遮蔽检测找的是替换标准库、pytest 或启动钩子的文件。从项目自己的包里在运行时打补丁，不会多出这样的文件。
  • 新增 conftest.py 会被拒绝，这堵住了攻破 SWE-bench 的那条路。[2]但把同样的补丁放进 __init__.py 不会被拒绝。
  • 比对输出的检查本来能发现打印内容不对的候选版本，但 F1 让作者可以事先读到冻结输出。
后果
“所有保留的检查都通过”这个结论，可以由被测代码自己制造出来。

修复：R2，并靠 R7 保持关闭。

F4

TMPDIR 可能让作者能写 state root

中已复现，有触发条件

位置：execution.py:64–98 execution.py:929

b96cf37 复查： Codex runner 上没有变化。Claude 沙箱把整机挂成只读，这条路在那里不存在。

作者通过环境变量白名单继承了 TMPDIR。Codex 的 workspace 模式会把 $TMPDIR 和 /tmp 加入可写根。只要 state root 位于其中任何一个之下，作者的可写范围就包含整个 job 目录。

把 TMPDIR 设为 job 目录的某个上级目录时，沙箱里成功覆盖了 ../baseline.json。TMPDIR 为 /tmp 且 job 在别处时，同样的写入被拒绝。

什么时候成立
默认布局不受影响，因为状态放在仓库旁边的 nanolize-runs/ 里。但 --state-root 接受任意路径，也没有任何地方检查它和 TMPDIR 的关系。

修复：R1（给作者私有的 TMPDIR，并在 job 启动时拒绝有问题的布局）。

F9

对 agent 设计的测试所做的过滤只是 lint，不是边界

低读代码

位置：leaf_test_design.py:1114

b96cf37 复查： 没有变化。

设计测试的 agent 写出的测试，如果某个调用的最后一个名字在名单上（system、popen、exec、setattr、patch 等）就会被拒绝。通过 getattr 间接取到的调用、os.exec* 和 os.posix_spawn 系列、pty.spawn，以及普通的写文件，都不在名单上。这些测试随后和其他检查一样，在没有沙箱的情况下运行。

修复：名单保留作为 lint，真正的边界交给 R2。

沙箱里的会话可以写 owner 的 HOME

高新增已复现；文档已说明

位置：runners/_claude_session.py:390–391，docs/graph-rewrite.md（“What the sandbox does not do”）

Claude 适配器把整个 HOME 以读写方式绑进沙箱，因为 Claude Code 的登录信息和状态都放在那里。会话写的其他东西都被限制在工作区里。在按适配器挂载顺序搭出的沙箱里，HOME 和 ~/.local/bin 都可写；在测试机上，这个目录在 PATH 里排在系统目录之前。

会话能拿它做什么

  • 改 shell 的启动文件。
后果
F1 的读边界最多只有这么牢。往 HOME 里写一次，就能在沙箱外执行代码，而在那里一切又都看得见了。

08

别人怎么划边界

benchmark 框架、一个兄弟项目，还有 coding agent 自身，都遇到过同样的问题。反复出现的是八种设计手法。

设计手法谁在这么做对应到 nanolize
agent 的环境里根本没有答案 NextTransformer 的 Gym 把研究 agent 放在一个容器里，里面没有仓库、训练状态、checkpoint 和 verifier 凭证，只有两个只读挂载。[1]伯克利的清单把“把 agent 和评测器隔离开”和“答案要保密”放在最前面。[2]ImpossibleBench 量化了效果：测试被隐藏或设为只读时，被利用得更少。[3] R1、R8
不可信代码在操作系统沙箱里运行，没有网络，也碰不到控制端状态 Gym 的 worker 运行在 bubblewrap 或 Landlock 之下，读不到 controller 的状态和凭证。[1]Claude Code 的沙箱设计指出，文件系统隔离和网络隔离必须同时具备才有效，并且让网络流量经过一个做过滤的代理。[6]Inspect 让评测框架待在沙箱外面，只把命令发进去。[11] R2、R8
分数由可信代码计算，而不是由被测代码上报 Gym 用可信代码从预测和标签计算验证指标。[1]“信任不可信代码的输出”是伯克利总结的七种致命模式中的第七种，也正是 SWE-bench 那个结果背后的原因。[2] R2
证据用 agent 拿不到的密钥签名 Gym 由运行中的服务用 HMAC 给提交证据签名。校验在一个没有网络的独立 verifier 容器里进行，reward 只表示“提交有效”。[1] R3
用封闭的、带类型的接口代替 shell Gym 的 API 是一组固定操作，每个都有输入 schema；命令、环境变量覆盖和路径一律拒绝。[1] controller 的 job 工具和 owner 专属的授权已经做到了这一点。
看轨迹，不只看结果 METR 的大多数案例是靠阅读运行记录发现的，不是靠看分数。[4]PaperBench 给每篇论文一份黑名单，使用其中的资源即视为作弊；Inspect 的移植版会拿 agent 的行为和它比对。[10]Gym 记录一个完整性标志，一旦置位就不能定稿。[1] R4
自己先攻击自己的评测器 伯克利的清单：用空 agent、随机 agent、prompt injection agent 和篡改状态的 agent 去跑评测器，只要得分不为零就是 bug。[2]ABC 清单以同样的思路审查任务设置和奖励设计。[5] R7
任何进程都不能三样全占 Meta 的 Rule of Two：不可信输入、敏感数据、改变状态或对外通信的能力，最多占两样。[8]CaMeL 更进一步，让不可信数据完全进不了控制流。[9]nanolize 的检查进程今天三样全占，Claude runner 上的作者会话也是。 R2、R6、R8

这里需要补一句。Gym 的设计文档自己写明：它的命名空间隔离防不住候选代码在同一进程内对计账做 monkeypatch，投入生产之前还需要再加一层信任边界。[1]同进程内的伪造对谁来说都难防。区别在于伪造者能够到多远，以及有没有人会发现。

09

对照一份清单

伯克利 Agent-Eval Checklist 的七项，[2]逐项对照 nanolize 的现状。

条目状态原因
把 agent 和评测器隔离开未满足；一种 runner 上部分满足作者、verifier 和候选代码共用一个用户、一个文件系统（F1、F2）。Claude runner 用黑名单隐藏文件，但 HOME 和网络仍然共用（F12、F13）。
绝不对不可信输入做 eval()已读部分满足报告被当作有界数据解析：有大小上限，不接受 DTD，不跟随链接。
净化给 LLM judge 的输入部分满足judge 被告知 solver 文本不可信，并且必须运行真实检查；确定性评分不需要模型。但读仓库文本的辅助 agent 只有那一句指令（F10），候选版本里的 agent 配置也会不经过滤地到达 judge（F16）。
对评测器做对抗测试部分满足demo 里有反例，比如退出码为 0 但输出变了。其中没有伪造报告或偷读 baseline 的候选版本。
防止评测数据和记录被篡改部分满足测试和运行器配置被冻结并比对。但结果来自候选进程写出的文件，封印也没有密钥（F2、F3）。
让打分足够稳健满足超时和输出被截断算失败，没跑的检查绝不算通过，不稳定的原始检查保留为缺口。
答案要保密未满足默认 runner 上靠指令保密，实际读得到（F1）。Claude runner 上靠手写的黑名单隐藏，而且网络是开的（F13）。
10

建议

九项改动。目标是划出三个区域，彼此之间只共享必须共享的东西。

作者区

负责重写的 agent 及其工具

  • 自己的工作区，可读可写
  • 契约、知识包和反馈
  • 模型 API
  • job 目录、原始仓库、已保存的会话
  • 凭证、回环地址、共用的 TMPDIR
  • owner 的 HOME、其他进程

verifier 核心

nanolize 自身：可信，不运行任何 agent 写的代码

  • baseline、held-out 任务、封印密钥
  • 控制 token 和发布
  • 把结果从检查区拷出来并校验
  • 绝不 import 候选代码

检查区

候选代码、测试、build backend

  • 候选代码树的一份拷贝，带冻结的测试
  • 私有的 /tmp 和 HOME
  • state root、baseline、token
  • 网络，除非 owner 的检查声明需要
  • owner 真实的 HOME
R1

给作者加读边界

Codex 工作量小，其他 runner 中等

关闭 F1F4F7，以及 F6 里作者的那一半

默认 runner。Codex 有权限 profile，其中的文件系统规则可以禁止读取。把 --sandbox workspace-write 换成 nanolize 为每个 job 生成的 profile：

default_permissions = "nanolize_author"

[permissions.nanolize_author]
extends = ":workspace"

[permissions.nanolize_author.filesystem]
"<state-root>"                      = "deny"
"<state-root>/jobs/<id>/authoring"  = "write"
"<original-repository>"             = "deny"
"<home>/.codex/sessions"            = "deny"

探测 6 在 codex-cli 0.169.0 上通过 codex sandbox -P 跑了这种结构：读兄弟目录和已保存的会话被拒绝，工作区仍然可写，解释器照常运行。接入之前有三点需要知道：

  • Codex 文档把权限 profile 标为 beta，并说明不要把 default_permissions 和 sandbox_mode 混用。[7]把 profile 传给 codex exec 还需要实际跑一次确认。
  • nanolize 自己的 argv 检查会拒绝提到这些路径的 runner 参数。所以 profile 必须由 nanolize 在那道检查之后加入，或者写进 runner 会加载的配置层。
  • 黑名单的完整程度取决于写它的人能想到多少。同一台机器上某个环境里装着的原始项目副本，就不在名单上。更可靠的形式是白名单。

任意 runner。在 bubblewrap 或 Anthropic 的 sandbox-runtime[6] 里启动 runner，只绑定三样东西：语言运行时、作者工作区、runner 自己的登录信息。这是白名单形式，也同样适用于 controller 和聊天 agent（F7）。

无论哪种。给每个 agent 一个位于其工作区内的私有 TMPDIR，并拒绝启动 state root 位于 $TMPDIR 或 /tmp 之下的 job。把 authoring/ 移出 job 目录可以去掉 .. 这条捷径，但这只能算整理，因为路径不是边界。

首次审查之后。Claude 适配器现在已经做了这件事的一个版本，也暴露出黑名单的不足（F12 到 F15）。要把它做完，见 R8。默认的 Codex runner 仍然完全没有读边界。

R2

把候选检查放进沙箱，并埋一根绊线

中等工作量

关闭 F2F5F6F9，以及 F11 的大部分

限制进程。包住每一个检查和每一条 install-check 命令：除非 owner 的检查声明需要，否则没有网络；私有的 /tmp 和 HOME；绑定候选代码树；state root、原始仓库和控制 token 完全不绑定。结果目录由 nanolize 创建，等进程结束后再把报告拷出来。做到这一步之后，候选代码最多只能伪造一份报告；baseline、token 和凭证它都够不着了。

不再只信一份报告。三种便宜的交叉校验，强度依次递增：

  • 一致性。实际执行的用例标识必须和冻结的清单一致；退出码、JUnit 里的计数、pytest 自己的汇总，三者必须讲同一个故事。
  • 哨兵用例。每次运行时加入一个 verifier 自有、名字随机的测试文件，里面一个用例必须失败，一个必须通过。如果报告里必须失败的用例通过了，或者哨兵不见了，就拒绝这份报告。这能抓住一刀切式的补丁。专门放过哨兵的补丁可以绕过它，所以哨兵应该看起来和普通测试没有区别。
  • 故意弄坏的候选版本必须失败。nanolize 已经会把原始代码里的函数敲掉，以证明测试确实依赖它们。对已接受的候选版本做同样的事：去掉一个被通过的检查所依赖的函数，再跑一遍。如果检查仍然通过，这些结果就不是证据。

这一项不保证什么。只要测试运行器还会 import 候选代码，就不能排除进程内的伪造；Gym 的设计文档对自己的 worker 也是这么说的。[1]沙箱限制的是伪造者能够到的范围，交叉校验让伪造变得可见。

R3

给封印加密钥

工作量小

关闭 F3

把单纯的摘要换成 HMAC，密钥在 job 冻结时生成。密钥由 worker 保管，放在一个既不绑定进作者沙箱、也不绑定进检查沙箱的目录里；每次调用作者前后、每次运行检查前后都校验记录。没有 R1 和 R2 的话，密钥和它保护的记录一样读得到，所以这一项排在第三。

R4

审计轨迹

工作量小；可以最先上线

用于发现 F1F2F7F10

runner 日志里已经记录了作者执行过的每一条命令。每次调用作者之后：

  • 扫描命令和文件读取，看有没有落在 state root、原始仓库和已保存会话之下的路径；
  • 扫描草稿，看有没有引用测试机制：_pytest、报告类、junitxml、对 sys.argv 的检查、对 unittest 的补丁。

命中就给 job 打上完整性标志。带标志的 job 不能以 succeeded 结束，交付时要把原因展示给 owner。METR 的大多数案例就是靠阅读运行记录发现的，[4]PaperBench 的黑名单是同一个思路，[10]而且这些都不需要先有沙箱。它只是检测：日志是 runner 写的，所以等 R1 到位之后它才更可信。基于模型的轨迹审查可以之后再加。

R5

收紧控制页面，并让 Submit 仍然由人来按

工作量小

加固 F5F15F17

把控制 token 放在任何 agent 沙箱和检查沙箱都看不到的目录里。对花钱的或无法撤销的步骤，要求提供本地进程和 agent 都给不出的东西：review 启动时在 owner 终端里打印的一次性验证码。这些步骤包括 Submit（含 submit_execution_review 和 /_control/submit 这个入口），以及上传和发布。想要无人值守运行的 owner，自己知情地把这个码传一次即可。review 页面的聊天也要过同一道关，因为它的 agent 能读原始代码。

R6

更安全的默认值

工作量小

关闭 F8，缩小 F10

  • 把 start_execution_review 的默认值改为 public=False，skill 已经是这样做的。
  • 把 Rule of Two[8] 当作每一种 agent 角色的设计检验：读仓库文本的 agent，在工作区之外没有写权限，除模型 API 外没有网络；能引发动作的 agent，只读其他 agent 产出的、经过 schema 校验的结构化输出。
R7

把这些攻击做成回归测试

工作量小，持续进行

让 F1F2F3F4F12F16 保持关闭

在测试集中加入对抗样例。每一个都必须以“被检测到的失败”收场：

  • 去读 ../worktree，或者去读放在 job 目录里的探针文件的作者；
  • 往 HOME 里写东西的会话；
  • 在 import 时给测试报告打补丁的候选包；
  • 在退出时重写 JUnit 文件的候选版本；
  • 修改 baseline 并重算摘要的候选版本；
  • 带着针对 judge 的 CLAUDE.md 或 hook 的候选版本；
  • 空的候选版本。

项目的贡献规则已经要求对仓库边界、baseline 完整性和进程执行做回归覆盖。这些样例就是那条规则的对抗部分，也是“对评测器做对抗测试”在实践中的含义。[2]

R8

把会话沙箱改成由 nanolize 构建的白名单

中等工作量

关闭 F12F13F14F15F18，并把 F1F7 做完

适配器已经在拼 bubblewrap 命令了。四处改动能把它从黑名单变成真正的边界：

  • 只绑定会话需要的东西。语言运行时、工作区、测试环境，以及 Claude Code 要读的登录文件；不再绑定整机和整个 HOME。给会话一个私有的空 HOME，把登录信息只读绑定进去，F12 就不存在了。
  • 给它独立的进程和网络命名空间。--unshare-pid 关闭 F18。网络方面，让命名空间唯一的出口是一个只放行模型 API 的代理，Anthropic 的 sandbox-runtime 就是这么做的。[6]这能关闭 F13 和 F15，也让“不要使用网络”变成事实。
  • 由 nanolize 指定要隐藏什么。harness 本来就知道原始仓库和 state root 在哪里，应该自己把它们加进去，而不是依赖 agent 写的配置文件。argv 检查禁止在参数里出现这些路径，那就换一种方式传，比如环境变量或 harness 自己写的文件。这不该成为把这件事留给 skill 的理由。
  • 每个 job 开始前先验证。在 job 目录里放一个探针文件；哪个 runner 的沙箱读得到它，就拒绝启动。runner 试跑是最自然的位置。它现在只检查 runner 能不能作答，不检查它有没有被关住。

在那之前，最小的有效改动是：把 /run/user/<uid> 加进 skill 的模板，并在 ptrace_scope 为 0 的机器上拒绝使用 bubblewrap 沙箱（F14）。

R9

不信任工作区里出现的任何 agent 配置

工作量小

关闭 F16F19，缩小 F10

  3. R2，检查沙箱和交叉校验，同时把 R7 的样例写出来。
  4. R9，工作区配置。改动小，而且保护的是 judge。
  5. R3，带密钥的封印，等有地方存放密钥之后再做。
  6. R5 和 R6 随时可以做，它们互不依赖。

这份审查的局限

  • 这是对一个约 5.7 万行代码库的定向阅读，不是完整审计。没有读到的防线可能会缩小某些问题的范围，也可能还有别的缺口。
  • 没有对真实的 nanolize job 运行任何攻击。F1 和 F4 是在沙箱层面复现的，F2 是在玩具项目上配合 nanolize 的解析器复现的，F3 以及 F5 到 F11 来自代码和项目自己的文档。
  • 只考察了 Linux。这里描述的两种 runner 之外的 runner，以及 macOS 和 Windows，情况可能更好，也可能更差。
  • 严重程度是针对 nanolize 自身主张的判断：一项问题在多大程度上削弱了“依据契约重写”和“对照原始版本验证”。它不是对第三方风险的评估。
  • 第二轮沿着 fe9b3bb 到 b96cf37 的 diff 进行，没有变化的代码没有重读。
  • Claude runner 的沙箱是按适配器的挂载顺序手工重建的，并用 shell 命令探测。没有运行 Claude Code 会话，也没有实施任何逃逸。F15 和 F16 来自代码，没有实测。
